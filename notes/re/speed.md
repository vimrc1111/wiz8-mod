# 戰鬥中怪物移動倍率（stage9 9.3，T）

靜態核對 `build/Wiz8.exe` v1.2.4 與 `build/wiz8.asm`，未執行遊戲。前 16 bytes 從 exe 讀取，檔內偏移＝VA−0x400000；只記位址、bytes 與自行描述的行為。

## 怪物攻擊／施法動畫倍率（stage10 A2，W）

| 位址 | 前 16 bytes | 行為 |
|---|---|---|
| 0x004c2b5d | e8be42feff8bcee86726000039ae3403 | A；怪物更新 0x004c2100 的 5-byte call，原目標 0x004a6e20，返回 0x004c2b62。thiscall：ecx＝怪物 B，一個 float m 堆疊參數，callee 清 4 bytes。僅替換 +1 起的 rel32。 |

- 序列集合依 [combat-anim.md](combat-anim.md) 候選 1：分類器 0x005430c0 的分類 6（9、0xa、0xb、0xc、0xe、0xf、0x10）、分類 7（0xd、0x11），以及施法序列 0x19；序列 4 排除。A＝DWORD[B+0x1d8]，序列為 signed BYTE[A+0xa4]。
- `anim_update` 以 fastcall 的 ecx 接 B、忽略 edx，保留唯一堆疊 float m 與 callee 清 4 bytes，再以 thiscall 呼叫原目標。A 為 NULL 或倍率為 100 時直接傳原 m；其餘由 `anim_m` 依序列與 BYTE[0x00683f94] 決定是否套用 `speed_eff`，保留原有半速等參數語意。
- exe 旁 `wiz8mod.ini` 的 `[combat] anim_speed_pct` 缺省 200，啟動記 `speed anim_speed_pct=<原整數>`，計算沿用 [10, 5000] clamp。A hook 獨立於 T／U 安裝，100% 也裝。
- build.sh 產生受 `#ifdef A` 保護的簽章；完整 16 bytes 不符時記 `sig-mismatch anim 0x004c2b5d` 並略過，取得寫入權限後只改 0x004c2b5e–0x004c2b61 四個 bytes。原 rel32 小端為 `be42feff`（signed −113986），新值為 `&anim_update − 0x004c2b62` 的小端 DWORD，實際值由 DLL 載入位置決定。刷新指令快取並還原頁面權限，成功記 `hooked anim 0x004c2b5d`。
- 沿用候選 1 已知限制：不鎖定序列邊界，戰鬥切換可能影響小數相位；近戰半程由外層輪詢放行，大倍率可能延後傷害至末格。實機存活、log 與手感留給 cc／MG 驗收。
- W 靜態驗證：預期 anim-rule 紅燈已重現；實作後 speed-rule、delay-rule、anim-rule 全部 PASS，check-sigs 的 51 條簽章相符。以實際安裝函式及生成 hooks.h 的暫存主機測試確認 16 個簽章 bytes 各自破壞時零寫入、取權限失敗時零寫入、成功只改四個 rel32 bytes，並還原權限、刷新快取與記指定 log。wrapper 以 i386 MinGW 的正式編譯旗標編譯通過，ecx 與 float 堆疊參數保留，尾呼叫原目標由其清 4 bytes。
- 本環境完整驗收停於 build.sh：Go 快取唯讀可藉 `GOCACHE=/tmp/wiz8-w-go-cache` 解決，但指定 Fusion Pixel／Noto Sans TC 字型均缺失，無法產生 atlas.h 與 DLL，check.sh 無產物可驗。未更換字型或放寬驗收；需具備既有字型的環境重跑四步驗收。

## +0x124 的生命週期與讀取者

- 0x004553a0 是反覆呼叫的物件更新，不是建構時的一次性拷貝。直接呼叫點包括物件集合迴圈 0x004a28b5、0x004aace6，以及 0x004c2623（各自取外層物件 +0x18 作為更新對象）。前兩點的兩個參數都是 0；第三點依外層狀態給參數。
- 寫入 0x004554dd 前，第一參數非 0、物件 +0xc 的 0x200000 位元、以及部分全域／物件條件都會跳過後續更新；0x006081e4 非 0 也會跳過本次拷貝。這個 byte 與戰鬥旗標 0x00683f94 是不同位置，不能把它當作戰鬥旗標。
- 同一次更新中，0x004554ee 讀 +0x124，第二參數非 0 時乘 0.5，於 0x004554fa 存回。後續 0x00455b27 在物件 +0x24 與 0x006081e4 均為 0 的路徑讀 +0x124，乘 +0x120 與係數 500，作為位移向量的一部分。
- 同函式後段 0x00455baf 會把向量長度換算後的速度存回 +0x124，0x00455bbe 視比較結果再以另一個上限覆寫。因此它既是速度副本，也是本次更新的工作欄位，不能當成永遠與全域速度相等。
- 結論：不存在「戰鬥前抄一次、之後完全不更新」的固定快取問題。進入戰鬥後，下一次通過拷貝條件的更新會取得 `speed_move` 的新值；略過更新的物件不會立即刷新 +0x124。這是靜態控制流結論，實際路徑與手感仍由實機驗收確認。

## patch 與執行期行為

- 我方 `volatile float speed_move` 明確 4-byte 對齊。只改 0x004546fd、0x00454722、0x004554de 的各 4 bytes，原值皆為 `ff506800`（指向 0x006850ff），新值為 `&speed_move` 的小端地址；DLL 載入位置決定實際地址。指令長度與其餘 bytes 不變。
- T 群簽章由 build.sh 從本表產生；三處全部通過 16-byte 比對且取得寫入權限才修改，失敗整組略過，保護權限以反序還原。同頁重複取得權限也保留原保護。
- 以 exe 所在目錄的 `wiz8mod.ini`，讀 `[combat] monster_move_pct`，缺檔／缺鍵預設 400；啟動 log 保留讀到的原整數，計算時限在 10–5000。只讀檔與遊戲速度／戰鬥旗標，不寫 0x006850ff、Wiz8.CFG 或選項畫面的 0x005a6f71／0x005a6f7f。
- attach 先計算初值，再於 DllMain 建立背景執行緒，不等待；建立失敗不裝 patch。背景每 50 ms 重新取 base 與旗標，非戰鬥回原值，非有限或非正 base 原樣通過。50 ms 是要求的輪詢間隔，排程可能延後，戰鬥切換與設定變更不是即時同步。
- 從初值旗標開始，首次觀察到 0→非 0 時記一次 combat log。正常有限值的 base／eff 乘 1000 後向零截成整數；非有限值無可表示整數，log 用 0，超出 LONG 的有限值飽和至邊界。此處只影響 log，`speed_eff` 不因此改值。


## 戰鬥事件固定延遲（stage9 U，第二輪）

### 盤點方法與事件識別

本輪以整份 `build/wiz8.asm` 搜尋 +0x30 的寫入，再以 exe 的程式碼區掃描固定立即值寫入編碼（含短／長位移）交叉核對；逐處回追物件來源，不以「偏移同為 +0x30」當成同類事件。下表 11 處非零固定毫秒值全部來自 0x0052e690，或由 0x0052e5c0 在 0x0052e679 轉交該建立端；它配置 0x38 bytes 並在 0x0052e729 呼叫建構子 0x0052c810。另列建構子的零值初始化，共 12 列。全部是 7-byte 指令，最後 4 bytes 為 imm32；簽章從寫入指令起算，不從 GetTickCount 呼叫點起算。

消費端 0x0052e00f 取 +0x30，非零時以 0x0052e01b 的 GetTickCount 減 +0x34；經過時間小於或等於延遲時仍返回，到下一次超過才繼續。零值直接略過此等待。它是共用事件佇列，故不修改消費端。

### 施法、怪物攻擊、閃避／受擊與排除項

- 施法 0x004ebfe0 至 0x004ec1df 沒有同類 +0x30 固定寫入；其就緒 gate 與效果處理不是這組毫秒值。怪物執行 0x004eb5a0 與怪物攻擊 0x00540170 也沒有額外直接固定寫入；結果路徑共用上表 0x00543734，不能漏算為玩家專用。已用 `build/decomp/anim.c` 的玩家攻擊與戰鬥分派結果輔助核對，bytes 仍以 exe 為準。
- 閃避／命中結果分支有呈現與事件建立，但未找到獨立於表中 11 處的同形固定延遲。受擊回應 0x0052f3c9 與死亡回應 0x0052f1b4 是額外發現的戰鬥可達寫入，但不是戰鬥專用：狀態傷害在 0x00503146 判旗標，非戰鬥仍經 0x00503156、0x00503162 到 0x0052a890；非致死可到 0x0052ab9d，致死經 0x0052ab89→0x00522fe0、0x00523221→0x0052abf0 再到 0x0052acc8。故兩處均保留，避免探索中狀態傷害的回應也被縮短。
- 同偏移但非本事件：0x0048f330 的時戳在 +0x28；0x0049cbe2 是浮點 1；0x0049e8be／0x004f3d12 為其他物件清值；0x004a0ce1 寫 5 且 +0x34 是物件結果；0x004d57df 寫 10、相鄰 +0x34 固定 30；0x0052d533 存 0x005ee748 指標；0x00586c09／0x00586c2b／0x00586c3a／0x00586c49 寫狀態 9／2／3／5。這些不列 D，亦不當作毫秒延遲。
- 盤點範圍是本 exe 可辨識的固定寫入與上述建立端；沒有把外部 DLL、動態資料值或其他物件的等待泛稱為已覆蓋。`build/wiz8.asm` 在 0x0056e800 的線性解碼失去邊界，本輪另由該已知呼叫目標重新解碼，確認所屬函式；不修改原材料。

### D 組安裝與倍率

- `[combat] event_speed_pct` 缺省 300，與 T 同用 exe 旁的 `wiz8mod.ini`。log 記讀取原值，計算 clamp 至 [10, 5000]；`delay_scaled` 用 unsigned 整數向下取整，ms≤600000 時分子至多 60000000，不溢位亦不需 CRT 除法 helper。
- D 僅包含表中五列標示 D 的指令。build.sh 從本表產生受 `#ifdef D` 保護的簽章。一次驗完全部 16 bytes，再取得全部立即值所在頁面寫入權限；任一不符記 `sig-mismatch delay 0x<VA>` 並整組略過，取權限失敗也不寫任何立即值。
- 各處只寫指令 +3 的 4 bytes，即 0x004ea0c1、0x0053eed6、0x00543737、0x00587594、0x0058a4f3；保留其餘 bytes 與指令長度。每處記 `delay 0x<指令VA> <原值>-><新值>` 並刷新指令快取，頁面權限反序還原，避免同頁重複取權限造成還原錯誤。
- attach 算一次，不另加執行緒。D 在 T 的執行緒建立／驗簽之前獨立安裝；D 失敗不阻止 T，T 失敗也不撤銷 D。T 原三處 0x006850ff 讀取 patch 不變。
- 靜態驗證不代表語音一定完整或攻擊後每段停頓都加快：這些常數只影響相應事件條件，仍需 cc／MG 指定的實機 log、存活時間與聽感驗收。本輪不執行遊戲、不寫遊戲目錄或 Wiz8.CFG。

### 規格疑慮（U）

- 「所有戰鬥路徑」與「非戰鬥路徑不改」在共用立即值 0x00505264、0x0052f1b4、0x0052f3c9 上重疊。依不改非戰鬥路徑的限制，三處列出但保留；僅改 imm32 無法按執行期戰鬥旗標區分。0x0056ec07 未證實戰鬥專用，同樣保留。
- 未發現需修改卻不是 imm32、或常數不在指令內的固定延遲寫入；delay-rule 與純函數實作一致。


### 本輪驗證結果

- 預期紅燈已重現：原 `speed.test.sh` 通過 speed-rule、因缺 `delay_scaled` 而在 delay-rule 編譯失敗；實作後兩者均 PASS。
- `WIZ8_EXE=build/Wiz8.exe` 的 `scripts/check-sigs.sh` 通過，50 條簽章相符；exe SHA-256 前綴為 `18a74ff61c65`。
- 暫存的主機測試直接擷取實際 `install_delay`／`sig_ok`，使用生成的 hooks.h 與 exe 原始 bytes，僅模擬 Win32 API，不執行遊戲碼：5×16 個簽章 bytes 各自破壞時全部零寫入；逐一讓 5 處取權限失敗時也全部零寫入；成功時只有五處 imm32 共 20 bytes 改變、值為 500／266／266／200／200，權限反序還原。此測試不替代 Windows 實機驗收。
